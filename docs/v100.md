# Tesla V100 port

The `sm_70` build is a peer hardware implementation of the same NInfer product surface as the
default `sm_120a` build. It accepts all five registered artifacts and retains Text, Vision, MTP,
prefix reuse, CLI, OpenAI Chat Completions/Responses, Anthropic Messages, and the 35B-A3B text-only
DFlash route. It does not add a second artifact format or model runtime.

## Build

CUDA 12.8 is required: CUDA 13 removed offline compilation for Volta. Configure the architecture
and compiler explicitly:

```bash
cmake -S . -B build-v100 -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CUDA_COMPILER=/usr/local/cuda-12.8/bin/nvcc \
  -DCMAKE_CUDA_ARCHITECTURES=70
cmake --build build-v100 -j
```

The Volta implementation uses native FP16 tensor cores through CUTLASS where appropriate, exact
Volta kernels for the registered attention/state contracts, and a vendored llama.cpp MMA
flash-attention kernel for long causal prefill. INT8 group-64 KV applies the registered normalized
D256 Hadamard transform to both persistent K and transient Q before the flash calculation.

NVFP4 dense MLP gate/up and down weights are uploaded in checkpoint-native layout and then permuted
in place into the Volta QPN fragment order during model load. The transform covers both the code
and scale planes. Row-scaled FP8 weights receive a corresponding code-plane permutation. Both
transforms preserve allocation sizes, record `VoltaQpnPrepacked` in the runtime weight view, and
release temporary device storage before inference. The artifact on disk is not rewritten. Decode
consumes the QPN layouts directly; wide prefill recognizes them and reconstructs FP16 for its
tensor-core GEMM. FP8 projection groups stage a shared FP16 activation once and reuse it across
their QPN launches.

Learned MTP accepts one through seven draft positions. The native INT8 attention kernel handles
verification widths through seven; the width-eight target round uses the qualified 6+2 attention
composition.

## Qualification

The default Volta run passes all 90 executed CTest cases; six real-artifact cases remain opt-in.
The complete attention contract suite passes for causal BF16/INT8/FP8 paths, packed Vision
attention, and DFlash context attention. The Qwen3.8-27B NVFP4 source-pressure case separately
passes its real-artifact state-materialization path, and the performance sweep loads and exercises
all five artifacts on 32-GiB V100 hardware. NVFP4 and K8V4 KV storage are not available on Volta.

### Context-lookup MTP

MTP has a lossless fast path for output that reproduces the request's own context. The host finds
the most recent earlier occurrence of the exact 16-token suffix and proposes up to fifteen tokens
that followed it. The longer verification topology is selected only when the learned MTP drafts
agree with the lookup prefix and every active batch row qualifies. Verification remains the
authority for every emitted token; a miss or disagreement uses the ordinary configured MTP window.
While lookup remains active, the graph produces one learned MTP token for the next qualification
check rather than rebuilding the full configured proposal window. The target still verifies all
fifteen lookup tokens, so this removes redundant serial draft work without weakening verification
or changing ordinary-generation proposals.

The copy qualification used the V100-PCIe-32GB, CUDA Graphs, INT8 group-64 KV, the optimized
proposal head at the Volta draft-window cap of four, greedy sampling, and a 172-token prompt that
both profiles reproduced verbatim.

| Qwen3.8-27B profile | Context lookup tok/s | Mean output/round |
|---|---:|---:|
| `groupwise-int` | **130.9** | 12.91 |
| `nvfp4` | **201.0** | 12.91 |

These are context-reproduction results, not general-generation headlines. On ordinary prose the
lookup eligibility test did not fire, output remained identical to the control, and decode stayed
within measurement noise.

## 35B-A3B prefill on tensor cores

Upstream, 91% of the 35B-A3B prefill ran on SIMT FP32 kernels: the sm_120 expert, router,
attention-input and output-projection routes use `mma_bf16`/`ldmatrix`, which trap below sm_80, so
the port had replaced them with scalar FMA kernels, and the Gated DeltaNet ran its sequential
per-token recurrence over every prompt token (the chunked stages trap too). An 8,192-token prompt on a
V100-SXM2-32GB (INT8 KV) now prefills in **1.3 s at `--prefill-chunk 4096`** (1.5 s at 2048), against
10.9 s upstream. Through `ninfer-serve` (MTP3, chunk 4096) prefill is 4,939 / 5,406 / 4,361 tok/s at
2K / 8K / 30K prompts (upstream 676 / 727 / 680), single-user decode unchanged (~155 tok/s). Perplexity on a 32K-token Spanish text (context 4096, stride
2048, INT8 KV): 3.4460 upstream, 3.4427 now.

GPU kernel time of that prompt (`--prefill-chunk 2048` for the first two columns; the rest is
norms, convolutions, routing scaffold and elementwise ops):

| Part | Upstream | First pass | Now (chunk 4096) | Route now |
|---|---:|---:|---:|---|
| Routed experts, gate/up (Q4G64) | 5.17 s | 0.59 s | 0.26 s | `sparse_moe_prefill_q4_gate_up_rega_kernel` |
| Routed experts, down (Q5G64/Q6G64) | 1.94 s | 0.33 s | 0.18 s | `sparse_moe_prefill_qx_down_rega_kernel` |
| Shared expert (W8G32) | 0.60 s | 0.09 s | 0.08 s | `sparse_moe_prefill_w8_shared_*_hmma_kernel` |
| Router (BF16) | 0.08 s | 0.08 s | 0.01 s | `sparse_moe_prefill_router_hmma_kernel` |
| W8 projections: attention input, 40 output projections, GDN input (W8G32) | 2.29 s | 0.30 s | 0.30 s | `CutlassSm70` (`w8_cutlass_sm70`; GDN input was already CUTLASS) |
| Gated DeltaNet | 0.45 s | 0.45 s | 0.14 s | chunked, `chunked/launch_volta.cu` |
| Flash attention (10 layers) | 0.16 s | 0.16 s | 0.17 s | unchanged |
| **Total GPU kernel time** | **10.84 s** | **2.18 s** | **1.29 s** | |

- **Routed experts** follow llama.cpp's Volta `mmid-hmma` kernel: each lane owns one weight row and
  decodes a 32-k step of its codes (Q4, or Q5/Q6 with the high-bit plane) straight into the A
  operand of `volta_mma_qk` with FP16 magic-number arithmetic, so weights never touch shared memory;
  raw codes run one 64-k group ahead, the BF16 activation slice is narrowed into a double-buffered
  FP16 tile one step ahead, one barrier per step. gate/up runs 8 warps (gate rows and the same up
  rows) and combines them through shared memory for SwiGLU; down issues the next item's first loads
  before the epilogue (K is only 512). The device-side job list and BN tiling are unchanged. MoE op
  (router to combined output, `ninfer_sparse_moe_bench --codec q4-q5`, eager, warm): 4.2 ms at
  T=2048 and 7.1 ms at T=4096 (first pass 6.9 / 12.8 ms).
- **Shared expert and router** are dense over every token: a 64-row x 64-k weight tile decoded to
  FP16 in shared memory, BF16 activations narrowed to FP16, four warps on `volta_mma_qk`.
- **W8 projections** use the same two-phase treatment as `gdn_input_proj`: dequantize the parent to
  FP16 scratch, cast the activations, CUTLASS Sm70 GEMM per output row range (`linear_add` adds the
  residual in a beta=1 epilogue). `ninfer_attn_input_proj_bench --format w8-qgkv`, T=2048: 23.3 ms
  to 1.18 ms; `ninfer_w8_linear_add_bench --k 4096`, T=2048: 7.66 ms to 0.53 ms. The route starts
  where it overtakes the SIMT kernel (its fixed cost is the dequantization, ~180 us for
  `linear_add` and ~370 us for the [9216,2048] parent): T >= 48 for `linear_add` (SIMT 165 us at
  T=40, 194 us at T=48) and T >= 32 for the attention input (380 us at T=32). Decode and MTP
  verification widths stay on the existing routes.
- **Gated DeltaNet** runs the chunked pipeline on sm_70 (`chunked/launch_volta.cu`): the same
  three stages and equations as the sm_80 route on WMMA m16n16k16 FP16/FP32, the WY inverse in FP32
  SIMT by 16x16 blocks, FP16 operands in the workspace (plus Volta-only FP16 copies of q and k),
  and the inter-chunk output term computed by the state stage while the state is on chip (h_chunk is
  never stored). `ninfer_gated_delta_net_bench --running --value-heads 32`, T=2048: 3.81 ms to
  1.20 ms. The state stage is the remaining cost (sequential over chunks, latency-bound).
- All accumulation is FP32; activations are narrowed BF16 -> FP16 for the Volta tensor cores.

## Preferred SXM2 device

On a dual-V100 host, set `NINFER_GPU_UUID` to the UUID of the intended SXM2 and invoke
`tools/v100/ninfer-sxm2.sh`. The launcher validates that the selected device is a
`Tesla V100-SXM2-32GB`, sets `CUDA_VISIBLE_DEVICES`, and runs `build-v100/apps/ninfer`:

```bash
NINFER_GPU_UUID=<sxm2-uuid> tools/v100/ninfer-sxm2.sh --help
```

Set `NINFER_EXECUTABLE` when the binary lives elsewhere. UUID selection prevents PCI enumeration
from silently moving benchmarks to a PCIe-board GPU. The executable still receives `--device 0`,
because CUDA remaps the selected UUID to logical device zero.

For Qwen3.8-27B serving, pass `--prefill-chunk 2048`. On the preferred SXM2 with the NVFP4 artifact
and INT8 KV, an 8,192-token prefill measured 1,137.0 tok/s versus 1,078.6 tok/s with the generic
1,024-token default, a 5.4% improvement.

## Constrained decoding (structured outputs)

Ported from upstream NInfer (Neroued/ninfer, Oct 2026): vendored XGrammar CPU core
(`third_party/xgrammar`, Apache-2.0) plus the GBNF / JSON object / JSON Schema / regex / choice
adapters in `src/text/`. Each constrained request owns a matcher in its Qwen output session; the
Engine installs a mask provider and the Program uploads packed vocabulary masks per sampled
position (ordinary decode, MTP and MTP-lookup verification, prefill finalization). The sampling and
speculative-acceptance kernels apply the mask on sm_70; CUDA graphs are unchanged because the mask
pointer travels in the per-round SamplingConfig. DFlash/DFlash2 engines reject constraints.

Protocol surface: Chat `response_format` (`json_object`, `json_schema`), `structured_outputs`
(`grammar`/`regex`/`choice`), `tool_choice` `required` or named, `strict` tools,
`parallel_tool_calls=false`, legacy named `function_call`; Responses `text.format` and tool choice;
Anthropic `output_config.format` and `tool_choice` `any`/`tool`. Constraints reject custom stops.

Differences from upstream: JSON grammars allow flexible whitespace (at most 64 characters per gap)
because forcing compact separators masks Qwen's preferred formatting tokens and degrades sampled
output; the Schema `format` keyword is accepted (known formats enforced, others annotations);
free `auto` tool use stays unconstrained (only strict/required/named/non-parallel tools compile a
tool grammar); a grammar violation ends that one request instead of failing the Engine.

Reasoning framing: the grammar's thinking prefix ends at the plain `</think>` marker (the same one
the output channels use) followed by at most 8 whitespace bytes, not at the exact
`\n</think>\n\n`. With the exact marker, a model close that landed on the thinking-budget boundary
(`\n</think>` emitted, `\n\n` not yet) let the canonical control text complete the marker early;
the grammar then rejected the rest of the control and the throw failed the whole Engine
(reproduced with a greedy request and `thinking_budget` one token before the natural close). A
control/grammar mismatch now ends only that request. Tokens a speculative round carries after the
stop token that completed the grammar are not violations. `NINFER_GRAMMAR_DEBUG=1` logs every
matcher rejection with the round, drafts and mask bit; an Engine failure logs its cause.

35B-A3B on GPU 9, MTP K=3, 4 lanes: JSON answer decode 198.9 tok/s unconstrained vs 195.8
json_object and 197.7 json_schema (temp 0, ~1,000 tokens); unconstrained prefill/decode unchanged.
